# Repository documentation ownership (DOCGEN-002)

This is a **read-only planning slice**, not the DeepWiki publisher. DOCGEN-001 continues to publish its immutable, repository-level generations under `.athanor/generated/documentation/`. It must not be mistaken for ownership of any package's editable `docs/` directory. The `ath docs plan-repository` command reports snapshot evidence, omissions and possible package-local paths; it does **not** write to them or authorize another command to do so.

```sh
ath index .
ath docs plan-repository . --snapshot <EXACT-COMMITTED-SNAPSHOT-ID> --limit 100 --json
```

The operation loads exactly the requested committed JSONL canonical snapshot; it never uses latest-snapshot fallback, walks the working tree for package facts, invokes Cargo, creates output directories, or starts a documentation provider. Missing/uncommitted snapshots fail. A committed snapshot with a missing JSONL payload (including a zero-row file) or manifest row counts that disagree with the decoded payload is rejected rather than treated as a partial snapshot; these checks are not cryptographic integrity proof. Its Store path must be confined to the project root, and symlinks along the JSONL read path are rejected. The composition-aware entry point deliberately bypasses injected Store factories: configuration must select JSONL and the operation uses the concrete JSONL reader, since a custom factory could write during initialization or load a different backend. Other Store backends are not admitted to this read-only operation.

The versioned public contracts are `athanor.documentation_repository_plan_request.v1` and `athanor.documentation_repository_plan.v1`. Requests have a portable exact snapshot identifier and a per-list display limit of 1–512. Reports contain totals and omitted counts for **each** list, deterministic ordering, and `writes_allowed: false`. No content is removed because of a filename suffix or a limit: omitted counts remain visible. Existing Markdown, READMEs, Cargo manifests, and other recognized ecosystem manifests are shown as source candidates separately from proposed output paths. README filenames with a Markdown extension are classified as `markdown`; other README filenames are classified as `readme`, not falsely asserted to contain Markdown. A foreign manifest (including a compatibility-spelled snapshot alias) fences its own directory subtree from an enclosing Cargo package; even an explicitly declared Cargo target inside that subtree remains visible but cannot propose an output page or claim Rust File ownership. A nested, independently verified Cargo package can still be reported. Shared Cargo/foreign roots do not receive output candidates. Every valid, uniquely identified `.rs` File is visible separately, including files that are not proven reachable as modules; malformed File claims only contribute issues and conservative path boundaries.

## Proof levels

1. A Cargo owner must be a unique canonical `Package` entity with a matching canonical `File` whose ID and `file://` key are unique across all snapshot entities and whose portable path has only one claiming `File` row (counting name, source, ownership and key even when their spellings agree), a package `package://` or distinct workspace `cargo-workspace://` key, source and ownership, and one unique, positive-confidence verified operations `SymbolDefined` fact pointing at that File in the **same** snapshot. Package/entity and definition fact IDs must match the extractor's deterministic keys and source span; aliasing manifest paths fail closed. Target/workspace fields are a restricted, versioned subset of the extracted manifest, not raw TOML. Snapshots indexed before these fields existed must be reindexed; the planner does not fall back to the live manifest. Index state advances from v96 to v97 so unchanged manifests **and Rust files** are re-extracted on the first new `ath index`, while v96 committed index pointers remain readable as historical artifacts; old state is not reused incrementally.
2. Workspace membership uses exact canonical declarations: literal directories, `.` and one-component directory globs such as `crates/*`; other glob expressions and invalid evidence fail closed. A verified root `[package]` without a workspace is standalone, not an unresolved child of its own `Cargo.toml`. The snapshot also carries the restricted workspace edition needed for inherited package editions; a package claiming both an inherited and a literal edition is rejected. Cargo 2015's different implicit target discovery default is accounted for; named explicit targets without a path require exactly one matching default root. Nested packages without verified membership, ambiguous workspaces, unknown enclosing manifests, and a manifest declaring both a package and a workspace at any repository depth do not receive output candidates for their shared documentation root. A second, unverified Package/workspace row claiming the **same** Cargo manifest through its source, ownership or path-bearing key is also a boundary; missing or contradictory language/kind cannot silently turn that shared root into an exclusive package owner. Malformed extra key fragments cannot hide such a claim or an unverified nested manifest, including when a directory name itself contains `#`.
3. Cargo target roots require both a declared/default target rule and a matching File in the same snapshot. An overlapping or unverified nested manifest, missing root, duplicated target identity (including two explicit declarations with the same portable name even if one root is missing), or shared source root prevents a target output proposal. A rejected File claim for a competing conventional Cargo-default root also prevents a unique target claim; one explicit target may still confirm the same default-discovered name and root. Output names are confined to the owning package's `docs/`; candidates already occupied by a human file or an existing directory (including a portable alias), conflicting parent directory spelling, nested manifest, or another proposal are suppressed. None of these checks substitute for publication-time filesystem preflight.
4. **Rust file identity is not Cargo target identity.** Newly indexed Rust symbols use `symbol://rust:file:<UTF-8-byte-length>:<source-file>:<qualified-name>` with matching source, ownership and identity version; definition and environment-usage fact IDs are file-qualified. The Rust linker resolves these new identities **within one source file only**, including calls, imports, direct same-module trait implementations and local containment. An impl fact cannot bridge qualified/imported paths, a generic self type parameter or a type alias to an unrelated same-named local type/trait declaration. Crate/module/impl-level unresolved `cfg`, test-harness or procedural attributes cannot create implementation/dynamic-dispatch bridges; the type and trait declarations must each be independently present. For changed Rust Files it drops prior file-local linker relations and relinks from current facts even when type/trait declarations are reused; an implementation removed from the source cannot survive through reused endpoints. Reusing a declaration never preserves old facts owned by a changed File: current extraction replaces them, and semantic fact changes invalidate that File's prior derived relations and diagnostics while the previous relation graph remains available to compute the affected dependency closure. A global `EnvVar` canonical row can originate in multiple Files but retain only one source; when that source changes or is removed, unchanged Files with verified first-party environment-usage facts are re-extracted to preserve a surviving variable with its actual source and ownership. These dependency re-extractions count as affected files, even if their content hash did not change. A SourceProvider without a nonempty content hash cannot prove a file unchanged: it is re-extracted, and a changed File entity is never treated as a reusable declaration that could carry stale File-owned impl/module facts. The built-in filesystem provider supplies a content hash. A batch that edits, adds and/or removes files joins the adapters' applicable invalidation scopes; a simultaneous add cannot mask removal or edit policy. It does not guess cross-file links from `crate::` or matching names; malformed/legacy keys in a mixed snapshot cannot bridge file scopes. Historical legacy-only snapshots remain inspectable but are not eligible for v97 incremental reuse or DOCGEN-002 symbol ownership.
5. The extractor records each parsed inline/external `mod` declaration as a file-owned syntax fact with its ordinal, inline ancestry, conditional/custom-path flags and evidence; a file-root module records its declaration count and opaque syntax. The read-only planner follows **individual, confirmed conventional module edges** from a Cargo target root: it validates the Rust root symbol and definition fact, every declaration fact and ordinal against the same File and snapshot, and checks that each declaration's name, presence flag and source span agree with its module entity before accepting exactly one `name.rs` or `name/mod.rs` File within the same package boundary. It does not traverse a source with opaque macro/attribute syntax or invalid facts; it skips individual conditional/custom-path declarations, duplicate declarations, unverified inline parents and missing or ambiguous Files. A rejected File claim for the competing conventional `name.rs`/`name/mod.rs` path (or a portable alias) still makes that choice ambiguous; it cannot be ignored to prove the other File. Case- or normalization-aliased File or directory paths are not accepted as module owners. Even a malformed/duplicate File row's portable name, source, ownership or `file://` key path, or manifest-shaped `Package` source/ownership/path-bearing key claims without a valid File, still fences nested projects and occupied output paths; it cannot supply an owner or become a reported source File. Contradictory File/directory claims (including a File used as another File's parent) likewise cannot prove a manifest, target root or module path. Snapshot alias checks use compatibility normalization and full Unicode case folding, but do not replace live-filesystem preflight. Repeated File claims from different targets/modules and their descendants are suppressed, not assigned arbitrarily. The bounded report lists each reachable File's logical `crate::...` module, `declared_in`, declaration fact, and `syntax` (`verified`, `opaque`, or `unavailable`); all valid `.rs` Files remain visible separately. Limits of 4,096 declarations per source, 128 levels and 20,000 graph visits produce explicit omissions. **Syntax evidence is not proof of a compiled configuration or a complete macro-expanded graph.**
6. A *partial* `rust_symbols` inventory projects individually verified definitions from confirmed, unambiguous, non-opaque module Files. The extractor records a conservative presence flag on the entity **and** its `SymbolDefined` fact: unresolved `cfg`/`cfg_attr`, test-harness `test`/`bench`, and unrecognized (potentially procedural) attributes on an item or enclosing inline module/impl/trait prevent an unconditional definition claim. The planner checks canonical file-qualified symbol/entity IDs, a single definition, matching same-snapshot Rust fact and File, exact source/evidence line span, and a uniquely declared inline parent chain. A trait method additionally needs a separately proven direct trait in the same File. An inherent method additionally needs a separately proven same-File struct/enum/union and a *distinct* `rust_inherent_method` syntax fact: only unqualified, single-segment local self types (including generic arguments) are recorded; qualified/imported types, type aliases and trait implementations are not guessed into local owners. The impl fact binds method and type IDs/keys, impl span, source/snapshot, conditional flag and deterministic ordinal. The planner translates parser-local qualified names to the logical Cargo-target module path; each row includes source/fact identities and, for methods, owner and impl evidence. Per-symbol failures are issues; the list has separate totals and display-limit omissions. This is **not** a complete API or compile-time reachability proof: macro output, arbitrary type resolution, conditional configurations, target-specific dependency semantics and cross-file Rust links remain unverified. Target `symbol_omission` is `rust_symbol_inventory_partial` where syntax has been confirmed, and Rust File omissions remain explicit. Target pages remain *path proposals* even when symbols are listed; `output_blocker` separately records why a path was withheld. Do not use this report to publish Rust symbol content.

A future publisher must establish complete target-specific symbol claims and citations from the exact snapshot, and introduce explicit per-package output ownership. It must recheck live path confinement, symlinks, case aliases, human-owned files, byte identity, and cancellation immediately before every write, using an atomic/rollback-safe publication protocol. An `.athanor.md` suffix alone is **never** ownership evidence. Rustok wiki integration should remain separate from package docs. Other ecosystems need their own resolvers (Node, Go, Python, .NET, etc.); their manifests currently remain visible as unresolved inputs, not guessed package owners.

The implementation and fixtures for this slice are source-prepared; focused build/tests and CI have **not** been run here. The user will run them separately.
